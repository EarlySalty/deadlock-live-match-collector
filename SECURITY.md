# Security and transparency

The current independent collector has no authorized complete game data source. The Windows desktop client can be evaluated in standby; the non-Windows CLI stops before key input. No live match values are collected or uploaded. Do not use it for live matches. Review the code and applicable game rules before use. A read-only design and automated scans do not guarantee safety or permission.

## Data boundary

The client sends versioned game telemetry to https://deutsche-deadlock-community.de/twitch/api/v3/live-match using HTTPS, a channel-specific bearer key and a 32 KiB body limit. The intended wire fields are documented in docs/contract. No screenshots, player names, Steam IDs, raw process memory, actual match IDs, credentials in the JSON, or arbitrary local files are intended to be uploaded. The future connection-key path uses bounded, non-echoing terminal input (128 input bytes, 512 input events), zeroizing application-owned buffers and direct HTTPS without implicit proxies; the key belongs only in the Authorization header. Invalid input exits; restart to retry. No guarantee of erasure of HTTP/TLS, OS, clipboard, swap or crash-dump copies. Do not collect/share dumps or logs with secrets. Update notifications link to the official release page; there is no automatic download, installation or execution. The backend is intended to retain only a short-lived RAM snapshot; its actual deployed behavior must be independently verified.

## Checks and verification

The CI configuration requires separate jobs for Rust formatting, strict Clippy and tests in default/all-features configurations, packaging tests, Cargo dependency gate and regenerated SBOM verification, RustSec, Gitleaks, workflow lint and two clean Windows x64 builds with read-only PE checks, hashes and ClamAV on the exact packaged EXE. The final build check requires every job to succeed. Local or hosted results are evidence only when actually executed. Dependabot proposes dependency updates. The release workflow requires a matching protected version tag, successful CI for the exact main commit, and hosted-runner provenance for the ZIP and standalone EXE. Stable releases additionally require the HTTPS routing/authentication preflight. Stable release creation remains blocked by the unconditional source gate. Only the exact owner-enabled desktop preview can advance through the trusted main GitHub-hosted release job after exact-SHA CI. Standing owner approval enables automatic numeric-version desktop previews; existing versions remain immutable. Ordinary CI has read-only GitHub rights; the release job has the permissions needed to attest and publish after checks. The same runner retains all binary files until the verified draft; no public binary Actions artifacts. VirusTotal is a mandatory fail-closed gate: no key, missing, stale, malformed or incomplete results, API failure, or any malicious/suspicious result blocks release. Submission requires explicit owner authorization; the standing owner-approved preview scope permits only the exact verified release EXE of the matching main version. The redacted engine-level report, checksums, Cargo SBOM and build evidence are retained even when a scan fails, without binary Actions artifacts. Successful new releases group the verified evidence into a separately attested security-evidence.zip with a shared SHA256SUMS for the three downloads. See docs/release-security.md for policies, prerequisites, limitations and signing preparation. Zero detections are not proof of safety. Pre-releases are not proof of production availability or real-game compatibility.

The [v0.3.0 desktop preview](https://github.com/EarlySalty/deadlock-live-match-collector/releases/tag/v0.3.0) is published for isolated evaluation, not for live matches. Verify its SHA-256 and provenance with GitHub's attestation verifier. ## Licensing and limits

Public source visibility is not a license grant. The owner must decide rights and licensing for the collector's own code; preserve all third-party notices. A Cargo SBOM is not a complete native/OS inventory. A same-host clean-build comparison is not independent provenance, and a cross-build is not a native Windows test. The application source gate and stable-release block remain unconditional. The preview exception fails closed without explicit owner authorization and successful checks.
