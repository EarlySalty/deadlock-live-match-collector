# Release security and evidence

## Release authorization — proposed v0.3.0 exception

- Stable releases remain unconditionally blocked while a complete authorized live source is absent. The sole exception is the public desktop preview **v0.3.0**, dispatched manually from main, with the exact reviewed main SHA in RELEASE_PREVIEW_SHA and RELEASE_HANDOFF_APPROVED=true. Other tags, modes, refs, events, or missing configuration fail closed. The source gate in the application is unchanged. This exception is not a production or real-match authorization.
- No workflow_run release trigger. The exact protected version tag and latest successful main push CI are checked before build, scan, attestation, draft creation and publication. publish and submit_to_virustotal default to false. Explicit upload also requires approved_exe_sha256 matching the exact transferred EXE; review the VirusTotal API/data-sharing terms first.
- Before setting RELEASE_SECURITY_APPROVED=true in each release environment, the owner must independently verify required main review and exact CI, immutable tags and restricted creation, main-only environments with an independent reviewer, prevention of self-review and no administrator bypass, and reviewed rights to distribute the code and assets. The variable is an administrative assertion, not automatic evidence. Approve the final collector SHA, not a moving branch.
- Build and scan have read-only GitHub permissions, separate from the attester (OIDC and attestation-write only) and publisher (release-write, no OIDC). The four jobs use independently protected environments: release, release-scan, release-attest, release-publisher. No binary Actions artifacts or untrusted workflow_run artifacts are consumed. The attestation describes the exact transferred subjects in the same trusted main workflow; it is not Authenticode or independent compiler provenance.
- The publisher verifies the draft's exact remote asset digests and ID, rechecks gates immediately before PATCH by verified ID, and verifies public assets after publication. A check is not atomic with mutation: exclude concurrent release/tag writers throughout the approved run. A failed post-publication check requires immediate owner incident handling; no automatic replacement/deletion or tag mutation.
- No public preview is authorized by this change alone. The proposed private handoff, named reviewers, exact SHA and tag authorization, scanner digest, approved tool/package snapshot, license/distribution decision and actual final scan remain mandatory.

## Proposed private handoff (requires explicit storage approval)

Use a dedicated private AWS S3 bucket with versioning, Object Lock COMPLIANCE, all four public-access blocks, bucket-owner-enforced ownership, TLS-only access, encryption at rest, audited access and a 30-day lifecycle (including noncurrent versions). No public URL, no ACLs, no shared access keys, no public GitHub binary artifact. This is a proposed implementation, not a provisioned service. Owner must verify configuration, costs, location, data protection and retention before enabling it. The workflow uses conditional creation, a seven-day compliance lock, exact returned version ID, SHA-256 and an allowlisted manifest binding source/tag/run/attempt/stage. Both retrieval jobs revalidate all bytes. A failed scan never reaches the second handoff. No executable is run from the handoff. Re-run all jobs, not a partial attempt.

In each environment configure RELEASE_HANDOFF_BUCKET, RELEASE_HANDOFF_ACCOUNT (12-digit expected owner), RELEASE_HANDOFF_REGION; set scoped credentials as RELEASE_HANDOFF_ACCESS_KEY_ID and RELEASE_HANDOFF_SECRET_ACCESS_KEY. Grant only required permissions on collector/ paths: release may put and read metadata on build objects; release-scan may read build versions and put/read metadata for scan objects; release-attest and release-publisher may only read scan versions. Needed S3 operations are PutObject, PutObjectRetention (writers), GetObjectVersion and GetObjectRetention (scoped as above). No deletion, policy, ACL or general bucket administration. Enforce conditional creation, encryption and compliance retention in bucket policy. Use narrowly scoped, rotated credentials; no credential in repository or logs. Validate the actual S3 integration with a harmless synthetic bundle before approval.

Set RELEASE_CLAMAV_IMAGE only to the independently approved official image digest in release. Set RELEASE_PREVIEW_SHA, RELEASE_HANDOFF_APPROVED and RELEASE_SECURITY_APPROVED separately in the four protected environments only after the documented checks. Configure named independent environment reviewers and prevent self-review. Move VirusTotal access to the protected release-scan environment if possible; do not expose its key to PR jobs. Obtain the EXE hash from the exact main CI evidence and compare to the protected build; if bytes differ, stop and obtain explicit approval of the new hash before dispatching again. The scan gate does not submit on a mismatch. No release is created if any gate fails.

## VirusTotal
The reusable release gate is `bash packaging/scan-virustotal.sh dist`. It invokes the existing exact-file verifier and preserves its nonzero exit status. The protected release job uses this same entry point; upload remains opt-in and requires the exact-hash authorization described in SECURITY.md. It does not authorize publication. Only the exact reviewed preview scope can advance.

Exact EXE SHA-256 must match checksum, file object ID and attribute SHA. Require all known category counts, actual per-engine entries with matching totals, at least 60 harmless/undetected verdicts, zero malicious and suspicious; analysis age at most seven days, no future dates. These conservative coverage/age defaults are proposed for review, not claims of sufficient safety. Failure/timeout/unsupported do not count as verdicts. Pending, malformed, stale, absent, quota and HTTP errors fail closed. GET retry max 3, minimum 60 seconds, Retry-After up to 120 seconds; no retry of ambiguous POST. Poll maximum eight times, 60 seconds apart. Existing stale reports need separately authorized reanalysis; no automatic submission on stale hash. API docs: https://docs.virustotal.com/reference/files and https://docs.virustotal.com/reference/analyses-object. Review API plan and data-sharing terms first. No key or raw API payload archived. Only allowlisted engine labels/categories/results and scan metadata are kept. No ignore/allowlist.

## Evidence and quarantine
CI and release attempt to retain only explicit text/JSON filenames for 90 days: run/SHA, checksums, toolchain, dependency gate and CycloneDX 1.5 Cargo graph, audit status, ClamAV output, VT summary and machine-readable results/exit code. If a step fails before a file is generated, that evidence cannot exist; failed step remains in Actions logs. Cancellation, runner failure or retention limits may prevent upload. No .exe, ZIP or raw API response in Actions artifacts. Copy text evidence to authorized private long-term archive if needed (owner approval); do not publish failed binary.
Proposed private quarantine: owner-approved private encrypted storage, no public links, MFA and minimal named security reviewers, audited access, object keyed by exact SHA/run/attempt, hash before/after transfer, immutable version or object lock, proposed 30-day TTL (extend only for documented investigation), deletion logged, no execution except separately authorized isolated test. No quarantine storage is provisioned. Until approved, failed runner binaries are ephemeral. The proposed release handoff is a separate, explicitly approved private staging location; failed VirusTotal candidates remain private until expiry.

## Dependencies and provenance
Full locked Cargo metadata includes transitive, dev/build and target-specific packages, names and source URLs checked against prohibited names/origins. The gate intentionally fails on old baseline. It cannot prove absence of copied/renamed code; independent source review is mandatory. Cargo-only SBOM is a conservative superset, not an exact linked binary inventory or OS/toolchain SBOM; toolchain evidence separately recorded. SBOM and lock hash tied to source SHA; verification regenerates the locked graph and compares exact SBOM bytes and gate metadata. This is not independent cryptographic authentication of the runner or artifacts. Hosted-runner GitHub provenance for ZIP, EXE and SBOM; verify against workflow, source digest and main. Attestations are not Authenticode signatures. Keep Gitleaks, RustSec, fmt, clippy, tests, ClamAV and Dependabot. Existing Gitleaks pin retained pending verified migration; checkout v6.0.2, upload-artifact v6.0.0 and provenance v4.2.2 pinned to upstream release commit SHA. Release build requires an owner-approved RELEASE_CLAMAV_IMAGE digest (no mutable stable tag); local/CI default scanner tag and apt packages remain mutable. Scanner DB version/hash recorded; an approved package snapshot and trusted current AV DB remain prerequisites. The Rust toolchain is already pinned.

## Authenticode preparation (not enabled)
Evaluate legitimate CA-backed signing or SignPath Foundation (eligibility/approval and license requirements must be confirmed). Owner must approve identity verification, terms, certificate, signing service, restricted build integration, human approval, and key custody (HSM/managed signing, never export private key to runner). No fake cert or SmartScreen bypass.
Integrate signing after compilation and before copying the final executable into the ZIP. Verify signature and timestamp chain with trusted Windows tooling (signtool verify /pa /all /v), require approved publisher identity. Then derive standalone EXE from ZIP, verify byte identity, calculate hashes, scan those final bytes, generate provenance; no modifications after scans. If signing fails, block signed release. Current build is unsigned; this is preparation only. Never describe an unsigned build as signed or imply reputation guarantees. No real sign/upload/release performed.
