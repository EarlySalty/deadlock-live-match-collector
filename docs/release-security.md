# Release security and evidence

## Solo-owner GitHub release policy — automatic desktop previews

- The owner grants standing authorization for automatic public desktop previews and submission of the exact verified release EXE to VirusTotal, starting with v0.3.1. Already published releases remain immutable. The canonical numeric version in Cargo.toml determines the tag and must agree with locked Cargo metadata. The stable release source block and the application source gate remain unchanged. No production integration or live-match permission follows from this exception.
- Push or merge to protected main starts ordinary CI. A successful completed **main push** CI run in this same repository triggers the release workflow. The event must match the exact current main SHA, workflow path, repository, event and branch. The release runner independently checks the latest successful exact-SHA CI and aggregate build job via the API, and checks its own checkout, remote main and Cargo version. No PR/fork code, upstream artifacts or caches are used. Manual dispatch on main is available for retry, with identical checks.
- The owner reviews changes through the existing main PR and strict CI rules; no separate human reviewer is required for the solo project. The release environment is main-only and has admin bypass disabled. Owner enables RELEASE_SECURITY_APPROVED, RELEASE_PREVIEW_ENABLED, RELEASE_AUTO_PREVIEW and RELEASE_VT_UPLOAD in the main-only release environment. The standing approval covers new numeric versions as pre-releases only, not stable releases or production operation. Disable RELEASE_AUTO_PREVIEW to suspend automatic releases.
- A single ephemeral GitHub-hosted release runner builds, scans, attests and publishes the same bytes, without S3 or another artifact store. Only explicit text/JSON evidence is uploaded as Actions artifacts. All binary files remain on that runner until the verified draft is created. No executable is run from a handoff. A failed gate prevents release creation. The tradeoff is that the release job needs contents-write and OIDC/attestation permissions throughout its lifetime; GitHub job permissions are not step permissions. This is restricted to the trusted protected main workflow, pinned actions, no persisted checkout credential, and GH_TOKEN, VirusTotal key and release tag deploy key provided only to the steps that need them. Build scripts and dependencies are part of the trusted computing base. Ordinary CI has read-only permissions.
- After all checks and provenance verification, push the exact version tag using a dedicated repository-scoped SSH deploy key (never force or update). GitHub rejects the built-in Actions integration as a tag ruleset exception. The creation-only ruleset permits repository deploy keys; the dedicated release key must remain the only write-enabled deploy key. Its private half is stored in the main-only release environment as RELEASE_TAG_DEPLOY_KEY, exposed only to the tag step, loaded in memory through an ephemeral SSH agent with GitHub's pinned public host key, and removed with the agent after use. A separate active v* immutability ruleset blocks updates and deletions without exceptions, including for deploy keys; main remains protected with no deploy-key exception. The key can write unprotected refs, so no other use is authorized. Repository default workflow permissions remain read-only. Existing tag must match the exact main SHA. Existing public release is not rebuilt or replaced. An existing draft blocks automatic creation; inspect its evidence before any recovery. Concurrent external release/tag writes must be excluded by the owner.
- Create a draft only after all gates. Verify all uploaded asset SHA-256 digests and IDs. Immediately recheck package, VirusTotal, dependencies, provenance, exact main/tag/CI and draft identity, then PATCH by verified release ID as prerelease with make_latest=false. Verify the public assets after publication. Checks are not atomic with mutation; post-publication mismatch requires owner incident handling. No automatic asset replacement/deletion or tag mutation.
- RELEASE_CLAMAV_IMAGE is the owner-approved official image digest. All previous scanner thresholds, RustSec, Gitleaks, locked dependency checks, reproducible builds, native Windows render tests and provenance remain mandatory. The binary is unsigned. Native real-game acceptance remains pending and the preview release notes state this limitation.

## One-time repository setup

- Create a dedicated Ed25519 deploy key for this repository only, with write access. Store the private key as the encrypted release-environment secret RELEASE_TAG_DEPLOY_KEY, not in the repository, logs or chat. Verify that no other write-enabled deploy key is present.
- Change the existing release-tag creation ruleset to target refs/tags/v* with a creation-only rule, no excluded versions, and a DeployKey actor (actor_id null, bypass_mode always). Do not change the separate immutable version-tag ruleset or the protected-main ruleset. Both must remain active with no bypass actors.
- Confirm the release environment is main-only and repository default workflow permissions are read-only. Set RELEASE_AUTO_PREVIEW=true only after these prerequisites and the standing release and VirusTotal authorization have been verified.
- Keep the existing scanner, dependency and exact-SHA CI checks. Disable RELEASE_AUTO_PREVIEW to stop releases; revoke the dedicated deploy key if its custody is in doubt.

## VirusTotal
The reusable release gate is `bash packaging/scan-virustotal.sh dist`. It invokes the existing exact-file verifier and preserves its nonzero exit status. The protected release job uses this same entry point. Standing owner approval through RELEASE_AUTO_PREVIEW=true and RELEASE_VT_UPLOAD=true permits submission only of the exact verified EXE of the authorized main desktop preview build, not arbitrary files, local builds or stable releases. The hash is calculated from the packaged bytes and verified against the checksum before upload. It does not authorize publication. Only the exact reviewed preview scope can advance.

Exact EXE SHA-256 must match checksum, file object ID and attribute SHA. Require all known category counts, actual per-engine entries with matching totals, at least 60 harmless/undetected verdicts, zero malicious and suspicious; analysis age at most seven days, no future dates. These conservative coverage/age defaults are proposed for review, not claims of sufficient safety. Failure/timeout/unsupported do not count as verdicts. Pending, malformed, stale, absent, quota and HTTP errors fail closed. GET retry max 3, minimum 60 seconds, Retry-After up to 120 seconds; no retry of ambiguous POST. Poll maximum eight times, 60 seconds apart. Existing stale reports need separately authorized reanalysis; no automatic submission on stale hash. API docs: https://docs.virustotal.com/reference/files and https://docs.virustotal.com/reference/analyses-object. Review API plan and data-sharing terms first. No key or raw API payload archived. Only allowlisted engine labels/categories/results and scan metadata are kept. No ignore/allowlist.

## Evidence and quarantine
CI and release attempt to retain only explicit text/JSON filenames for 90 days: run/SHA, checksums, toolchain, dependency gate and CycloneDX 1.5 Cargo graph, audit status, ClamAV output, VT summary and machine-readable results/exit code. If a step fails before a file is generated, that evidence cannot exist; failed step remains in Actions logs. Cancellation, runner failure or retention limits may prevent upload. No .exe, ZIP or raw API response in Actions artifacts. Copy text evidence to authorized private long-term archive if needed (owner approval); do not publish failed binary.
Proposed private quarantine: owner-approved private encrypted storage, no public links, MFA and minimal named security reviewers, audited access, object keyed by exact SHA/run/attempt, hash before/after transfer, immutable version or object lock, proposed 30-day TTL (extend only for documented investigation), deletion logged, no execution except separately authorized isolated test. No quarantine storage is provisioned. Failed runner binaries are ephemeral and are never attached to public Actions artifacts. VirusTotal submission is external disclosure of the exact EXE under the owner authorization.

## Dependencies and provenance
Full locked Cargo metadata includes transitive, dev/build and target-specific packages, names and source URLs checked against prohibited names/origins. The gate intentionally fails on old baseline. It cannot prove absence of copied/renamed code; owner source review is mandatory. Cargo-only SBOM is a conservative superset, not an exact linked binary inventory or OS/toolchain SBOM; toolchain evidence separately recorded. SBOM and lock hash tied to source SHA; verification regenerates the locked graph and compares exact SBOM bytes and gate metadata. This is not independent cryptographic authentication of the runner or artifacts. Hosted-runner GitHub provenance for ZIP, EXE and SBOM; verify against workflow, source digest and main. Attestations are not Authenticode signatures. Keep Gitleaks, RustSec, fmt, clippy, tests, ClamAV and Dependabot. Existing Gitleaks pin retained pending verified migration; checkout v6.0.2, upload-artifact v6.0.0 and provenance v4.2.2 pinned to upstream release commit SHA. Release build requires an owner-approved RELEASE_CLAMAV_IMAGE digest (no mutable stable tag); local/CI default scanner tag and apt packages remain mutable. Scanner DB version/hash recorded; the apt package versions and trusted current AV DB are recorded; Ubuntu package sources remain mutable. The Rust toolchain is already pinned.

## Authenticode preparation (not enabled)
Evaluate legitimate CA-backed signing or SignPath Foundation (eligibility/approval and license requirements must be confirmed). Owner must approve identity verification, terms, certificate, signing service, restricted build integration, human approval, and key custody (HSM/managed signing, never export private key to runner). No fake cert or SmartScreen bypass.
Integrate signing after compilation and before copying the final executable into the ZIP. Verify signature and timestamp chain with trusted Windows tooling (signtool verify /pa /all /v), require approved publisher identity. Then derive standalone EXE from ZIP, verify byte identity, calculate hashes, scan those final bytes, generate provenance; no modifications after scans. If signing fails, block signed release. Current build is unsigned; this is preparation only. Never describe an unsigned build as signed or imply reputation guarantees. No real sign/upload/release performed.
