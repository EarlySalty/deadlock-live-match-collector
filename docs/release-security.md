# Release security and evidence

## Release authorization
- No workflow_run release trigger: a successful CI run is evidence, never authorization. Manual workflow_dispatch from main only, exact SHA and version tag checked against remote main and latest successful push CI run. publish defaults to false (draft only); submission to VirusTotal defaults to false. Neither a draft nor a published release may be created when any mandatory gate fails.
- Before setting RELEASE_SECURITY_APPROVED=true in the release environment, repository owner must independently verify main branch protection (required review and exact CI), tag ruleset v* with restricted creation/update/deletion and no uncontrolled bypass, release environment restricted to main with required independent reviewer, prevention of self-review and no admin bypass where supported. Variable is an explicit administrative assertion, not an automated proof of settings. Do not set it until the independent review of the final collector SHA is complete. No settings were changed.
- CI, prepare and the blocked release build job have only read permissions. The build job cannot publish or attest. The unconditional source block is retained and an additional unconditional handoff block replaces privileged steps. A future separate protected publisher/attester requires an approved private, immutable, digest-bound transfer of exact bytes (not a public Actions binary artifact), separate job-scoped minimal rights, and an independent review. No untrusted workflow_run artifacts, caches, refs or PR code consumed by release.
- Existing release checks verify main/tag/CI again before mutation. Stable preflight is routing/auth only, not functional evidence. The standalone draft script verifies all remote asset sizes, SHA-256 digests, names, uploaded state and unique IDs after creation; packaging/verify-before-publish.sh is a read-only prepublish gate for a future approved publisher, including tag/CI/provenance and remote draft ID. Missing/extra/mismatched assets fail closed. A check is not atomic with publication; restrict concurrent mutation rights and recheck immediately before publishing by the verified release ID. No publishing job is enabled.

## VirusTotal
Exact EXE SHA-256 must match checksum, file object ID and attribute SHA. Require all known category counts, actual per-engine entries with matching totals, at least 60 harmless/undetected verdicts, zero malicious and suspicious; analysis age at most seven days, no future dates. These conservative coverage/age defaults are proposed for review, not claims of sufficient safety. Failure/timeout/unsupported do not count as verdicts. Pending, malformed, stale, absent, quota and HTTP errors fail closed. GET retry max 3, minimum 60 seconds, Retry-After up to 120 seconds; no retry of ambiguous POST. Poll maximum eight times, 60 seconds apart. Existing stale reports need separately authorized reanalysis; no automatic submission on stale hash. API docs: https://docs.virustotal.com/reference/files and https://docs.virustotal.com/reference/analyses-object. Review API plan and data-sharing terms first. No key or raw API payload archived. Only allowlisted engine labels/categories/results and scan metadata are kept. No ignore/allowlist.

## Evidence and quarantine
CI and release attempt to retain only explicit text/JSON filenames for 90 days: run/SHA, checksums, toolchain, dependency gate and CycloneDX 1.5 Cargo graph, audit status, ClamAV output, VT summary and machine-readable results/exit code. If a step fails before a file is generated, that evidence cannot exist; failed step remains in Actions logs. Cancellation, runner failure or retention limits may prevent upload. No .exe, ZIP or raw API response in Actions artifacts. Copy text evidence to authorized private long-term archive if needed (owner approval); do not publish failed binary.
Proposed private quarantine: owner-approved private encrypted storage, no public links, MFA and minimal named security reviewers, audited access, object keyed by exact SHA/run/attempt, hash before/after transfer, immutable version or object lock, proposed 30-day TTL (extend only for documented investigation), deletion logged, no execution except separately authorized isolated test. No storage provisioned and no automatic upload. Until approved, failed runner binaries are ephemeral.

## Dependencies and provenance
Full locked Cargo metadata includes transitive, dev/build and target-specific packages, names and source URLs checked against prohibited names/origins. The gate intentionally fails on old baseline. It cannot prove absence of copied/renamed code; independent source review is mandatory. Cargo-only SBOM is a conservative superset, not an exact linked binary inventory or OS/toolchain SBOM; toolchain evidence separately recorded. SBOM and lock hash tied to source SHA; verification regenerates the locked graph and compares exact SBOM bytes and gate metadata. This is not independent cryptographic authentication of the runner or artifacts. Hosted-runner GitHub provenance for ZIP, EXE and SBOM; verify against workflow, source digest and main. Attestations are not Authenticode signatures. Keep Gitleaks, RustSec, fmt, clippy, tests, ClamAV and Dependabot. Existing Gitleaks pin retained pending verified migration; checkout v6.0.2, upload-artifact v6.0.0 and provenance v4.2.2 pinned to upstream release commit SHA. Release build requires an owner-approved RELEASE_CLAMAV_IMAGE digest (no mutable stable tag); local/CI default scanner tag and apt packages remain mutable. Scanner DB version/hash recorded; an approved package snapshot and trusted current AV DB remain prerequisites. The Rust toolchain is already pinned.

## Authenticode preparation (not enabled)
Evaluate legitimate CA-backed signing or SignPath Foundation (eligibility/approval and license requirements must be confirmed). Owner must approve identity verification, terms, certificate, signing service, restricted build integration, human approval, and key custody (HSM/managed signing, never export private key to runner). No fake cert or SmartScreen bypass.
Integrate signing after compilation and before copying the final executable into the ZIP. Verify signature and timestamp chain with trusted Windows tooling (signtool verify /pa /all /v), require approved publisher identity. Then derive standalone EXE from ZIP, verify byte identity, calculate hashes, scan those final bytes, generate provenance; no modifications after scans. If signing fails, block signed release. Current build is unsigned; this is preparation only. Never describe an unsigned build as signed or imply reputation guarantees. No real sign/upload/release performed.
